# 面后（AfterRound）· 5 分钟演示脚本

> 目标：5 分钟内让面试官看懂三件事——为什么做、做了什么、和市面工具有什么不同。
> 原则：每一步先给结论，再给画面；细节留到追问环节，不主动展开。

## 0. 演示前准备（T-10 分钟）

### 环境

1. 启动数据库：`docker compose up -d postgres`
2. 启动后端：按 [README「快速开始」](../README.md#快速开始本地开发) 导入 `.env` 后 `mvn spring-boot:run`
3. 启动前端：`cd frontend && npm run dev`
4. 打开 `http://localhost:5173`，确认页面无报错横幅

### 模型

- 「设置 → 模型服务」确认已有可用服务商，且设置了全局默认模型
- 点一次「连通测试」，确保演示当天上游可用

## 2. 逐步操作与话术

### 2.1 开场（0:00–0:30）

**点击**：停在首页或简历中心。

**话术**：

> 市面上的求职工具大多做「面试前」：模拟面试、题库、实时提示。但真实求职里更痛的是「面试后」——面完就忘，同类问题反复丢分，改了简历也不知道有没有用。面后补的就是这一段：把每场真实面试沉淀成结构化档案，跨场比较、归因，并验证改进是否生效。

**不要**：不要先讲技术栈，不要逐条念功能列表。

### 2.2 简历 → 五维报告（0:30–1:20）

**点击**：简历中心 → 点「张伟」这条简历。

**画面要点**：总分、五个维度条、优势 / 短板、原句优化、岗位方向、薪资可改。

**话术**：

> 简历分析用固定模板、固定五维权重和低温度，模型只负责评语和建议，总分由本地按权重计算，保证两次分析口径一致。薪资字段支持用户修正，重跑分析不会覆盖用户填的值。

### 2.3 岗位库 → JD → 匹配（1:20–2:05）

**点击**：岗位库 → 星河科技岗位 → 展示解析字段与最近一次匹配。

**画面要点**：JD 结构化字段（薪资 / 经验 / 学历）、匹配总分、三项维度、差距清单、准备建议。

**话术**：

> JD 支持文本、文件和截图三种导入，截图会先用视觉模型提取原文，再走同一套结构化解析。匹配分同样由本地按 50/30/20 加权，模型只输出分项和差距，不负责算总分。这里的差距清单会直接变成面试准备清单。

### 2.4 真实面试复盘（2:05–3:05）· 核心

**点击**：面试复盘 → 打开「星河科技 · 第 2 轮 · 交叉面」。

**画面要点**：转写文本、结构化问题列表、知识点标签、失分标签、总结、改进行动。

**话术**：

> 这是产品的核心。输入可以是录音、转写文本或手动笔记，目标是 5 分钟内录完。系统异步做结构化分析：拆出问题、标注知识点和失分类型、给出总结和 3 条改进行动。所有 AI 产出都可以改，确认后才写入改进看板。

**可选补充**（时间够时）：

> 分析失败会保留原文和错误原因，可以重试；同一投递的同一轮次只允许一份复盘，避免重复录入。

### 2.5 求职洞察（3:05–4:05）· 差异化

**点击**：求职洞察 → 保持「近 90 天 / 全部公司」。

**画面要点**：样本卡（投递 2 / 面试 5 / 已确认复盘 5 / Offer 1）、知识点失败率、失分频次、轮次通过率、公司画像、高频问题、漏斗、改进验证率、趋势。

**话术**：

> 单场复盘只是记录，跨场聚合才有洞察。这里能看到哪类知识点反复失败、哪种失分类型出现最多、哪个环节通过率最低。样本少于 5 场时只展示原始统计，不给出结论，避免过度解读。聚合全部在 PostgreSQL 里用 JSONB 做，不调用 LLM，所以又快又稳。

### 2.6 改进闭环 + Offer（4:05–4:45）

**点击**：改进看板 → 指向「已验证」的行动和证据；再切到 Offer 决策 → 对比 Tab。

**话术**：

> 改进动作有状态流转和验证证据，下一场面试可以回来标记是否生效，这样「改进」不是一句口号。Offer 用固定 12 行同维度对比，缺失项统一显示「未填写」，避免每个 Offer 字段不一样导致没法比。

### 2.7 工程质量（4:45–5:00）

**点击**：GitHub Actions 最近一次运行。

**话术**：

> 项目按契约先行开发：先改 OpenAPI，再实现后端并跑契约一致性测试，前端类型由契约生成。当前 88 个端点、后端 180 个测试、前端 26 个单测和 16 个 E2E，CI 三个 job 全绿。模型层是数据库驱动的多 Provider 网关，支持热切换和结构化输出修复。

## 3. 一句话差异化

| 类型 | 代表能力 | 面后的不同 |
|---|---|---|
| 模拟面试工具 | 出题、练习、评分 | 练习是可选；核心是真实面试数据 |
| 实时面试辅助 | 面试中提示答案 | 不做实时作弊；做面试后的沉淀与归因 |
| 笔记 / 表格 | 手动记录 | 结构化字段 + 跨场聚合 + 改进验证 |

## 4. 常见追问与回答

**Q：为什么不用 Spring AI / LangChain4j？**
A：项目需要会话级 Provider 绑定、调用级追溯、结构化输出修复和分层降级，这些框架给不了或会遮蔽协议细节；手写 OpenAI 兼容客户端约几百行，可控性更高。

**Q：结构化输出怎么保证稳定？**
A：JSON 模式 + 低温度 + 字符级本地修复 + 带错误反馈重试（≤3）+ AI DTO 与业务实体分离 + 本地兜底校验；模型不参与算总分。

**Q：为什么不做 RAG？**
A：几十到几百场面试约十几万字，远小于上下文窗口；结构化聚合 + PostgreSQL JSONB + 全文检索更直接，向量检索没有收益。

**Q：样本只有 5 场，洞察有意义吗？**
A：有，但只展示原始统计和明显模式；N<5 明确标注样本不足，不输出结论。产品目标是让用户先形成记录习惯。

**Q：为什么先做复盘而不是继续做模拟面试？**
A：模拟面试是红海，且练完仍然不知道真实面试哪里丢分；真实复盘的数据可以反哺简历、JD 准备和下一轮练习，闭环价值更高。

**Q：单用户、无鉴权，怎么产品化？**
A：数据表已预留 `user_id`，存储层用 `FileStorage` 接口隔离；产品化需要补登录、多租户、对象存储和限流，属于后续里程碑，不在当前范围。

## 5. 演示失败兜底

| 情况 | 处理 |
|---|---|
| LLM 上游超时 | 不现场等，直接打开已有已确认复盘，讲分析结构；说明异步 + 重试 ≤3 |
| 数据为空 | 用「岗位库 → 粘贴 JD 文本」最快路径现场导入，或直接展示洞察空状态文案 |
| 端口冲突 | 后端换 8081、前端换 5174，并同步 Vite 代理；或直接播放录屏 |
| 页面报错 | 刷新一次；仍失败则切到截图，不在现场排查 |

## 6. 演示后清理

- 演示数据可保留，便于下次演示；不想要时在对应页面逐条删除（删除会级联清理复盘、行动与文件）
- 停止服务：前端 `Ctrl+C`、后端 `Ctrl+C`
- 停止数据库：`docker compose stop postgres`（不要用 `down -v`，会清空数据卷）
