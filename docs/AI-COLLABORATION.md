## 0. 先看结论

- 这是一个**个人自用的 AI 求职辅助平台**：简历分析 → 岗位匹配 → 模拟面试 → 真实面试复盘。
- 技术上不是「多智能体框架」，而是**以确定性业务编排为核心的 LLM 应用**：模型负责理解与生成，状态机、计分、存储、权限边界由代码控制。
- 项目里真正可迁移到 Agent 岗位的能力：LLM 协议与流式、结构化输出稳定性、Prompt 与上下文工程、模型路由与热切换、异步任务与重试、可观测性与成本、契约与评测体系。
- 开发方式：**AI 深度结对**。作者负责目标、约束、验收与决策；AI 负责检索、实现、验证与文档。所有关键结论必须落到代码、测试、契约或仓库文档，而不是只停在对话里。

## 1. 项目全景

### 1.1 一句话介绍

> 职点（JobPilot）是一个面向个人求职闭环的 AI 平台：上传简历得到五维分析与岗位方向；导入 JD 做匹配与行情分析；用结构化模拟面试练习；最后把真实面试沉淀为可复盘、可统计的文档。

### 1.2 形态与边界

| 维度 | 现状 |
|---|---|
| 用户形态 | 单用户、免登录，`user_id` 固定为 1，由后端注入 |
| 部署 | 本地 Docker Compose / 本机开发；数据只在本地 |
| 数据 | PostgreSQL（业务数据 + JSONB）+ 本地磁盘（原始简历文件） |
| 模型 | 数据库驱动的 Provider / Model，可页面热更新；M1 使用内网 OpenAI 兼容网关 |
| 前端 | Vue3 + TypeScript + Vite，无 UI 库，design tokens |
| 后端 | Java 21 + Spring Boot 3.5 + MyBatis-Plus + Flyway + Tika + WebClient |
| 明确不做 | 多租户、登录鉴权、RAG / 向量库、前端 UI 框架、Spring AI 等 LLM 框架 |

### 1.3 当前里程碑

| 里程碑 | 状态 |

## 3. 架构与核心流程

### 3.1 逻辑架构

```
Vue3 SPA
   │  /api（开发期 Vite 代理；生产 Nginx 反代，SSE 关闭 buffering）
   ▼
Spring Boot
   ├── modules/llm      Provider / Model / 全局默认 / 场景绑定 / 连通测试
   ├── modules/chat     会话、两级模型切换、SSE 流式、消息追溯
   ├── modules/resume   上传、Tika 解析、异步分析、报告、删除
   ├── common/llm       手写 OpenAI 兼容客户端、结构化输出收口、JSON 修复
   ├── infrastructure   ProviderClientRegistry、LlmCallLogger、LocalFileStorage
   └── common/api       Result / PageResult / ErrorCode / 全局异常 / traceId
   ▼
PostgreSQL（业务 + JSONB + 状态机 CHECK） + 本地磁盘（resumes/<sha256>.<ext>）
   ▼
OpenAI 兼容上游（/chat/completions、/models、SSE）
```

### 3.2 核心流程一：简历上传到报告

1. 上传文件或粘贴文本；SHA-256 去重，重复上传返回已有记录。
2. 原始文件写 `STORAGE_ROOT`，解析文本落 `resumes.resume_text`。
3. 若已配置全局默认模型，自动进入异步分析；否则保持 `PENDING`，由用户点「开始分析」。
4. 分析任务：`PROCESSING → COMPLETED / FAILED`，自动重试 ≤3 次，重启后回收滞留任务。
5. LLM 输出 JSON → 本地修复 → 解析为 AI 中间 DTO → 本地计分与兜底 → 写 `resume_analyses`。
6. 报告接口返回五维横向条形数据、优势短板、原句优化建议、岗位方向、薪资（用户值优先）。

### 3.3 核心流程二：对话与模型切换

- 会话内 Provider + Model 两级切换；`PROCESSING` 时切换返回 409，终态 `LOCKED` 锁定。
- 消息逐条记录实际使用的 Provider / Model / traceId，支持事后追溯。
- SSE 流式输出；取消、异常结束、队列拒绝都有明确处理，不把残缺回答当成功。

### 3.4 核心流程三：Provider 热更新

- Provider = baseUrl + apiKey（AES-GCM 密文落库，对外掩码）；1 个 Provider 挂 N 个 Model。
- 任一 CRUD 后精确失效内存客户端缓存，无需重启。
- 新增服务商后自动拉取上游模型；唯一模型自动添加并设为全局默认，多模型勾选批量添加。

## 4. 关键设计决策（ADR 摘要）

| # | 决策 | 结论 | 理由 | 代价 / 风险 |
|---|---|---|---|---|
| 1 | LLM 框架 | 不引入 Spring AI / LangChain4j / AgentScope，手写 OpenAI 兼容客户端 | 热更新、结构化加固、分层降级是真实复杂度，框架不直接提供且遮蔽协议细节 | 自研与维护成本 |
| 2 | 文件存储 | 本地磁盘 + `FileStorage` 接口隔离 | 个人版不引入 MinIO；后续可替换 | 多设备需主机模式 |
| 3 | Provider/Model | Provider 不含 model，1:N；请求按 `providerKey + model` 定位 | 同一网关多模型不重复配 key | 需要双维度校验 |
| 4 | 会话切换 | 两级切换；执行中禁止切换（409），终态锁定 | 避免同一会话上下文语义漂移 | 前端需处理冲突态 |
| 5 | 配置来源 | 数据库驱动 + 页面 CRUD + 缓存失效 | 用户会换内网/GPT/DeepSeek，不能每次改 yml | 密钥加密与掩码必须到位 |
| 6 | 契约 | `contracts/openapi.yaml` 为唯一接口源，前端类型由契约生成 | 防前后端漂移；契约测试可机器验证 | 契约先行增加前期工作量 |
| 7 | 分析一致性 | 固定 Prompt + 固定五维权重 + 固定 `temperature=0.2` + 结构化校验 | 同一简历两次分析要稳定可解释 | Prompt 调整需谨慎 |
| 8 | 计分 | 总分本地按权重计算，不信任模型自报 | 防止模型改权重或算错 | 模型只负责分项与文案 |
| 9 | 异步任务 | 状态四件套（status + CHECK + error + retry_count），重试 ≤3 | 重启不丢、可查、可重试 | 需要启动恢复与并发守卫 |
| 10 | 不做 RAG | 几十至数百场面试约 15 万字，远小于上下文窗口 | 向量检索收益低、组件成本高 | 数据量变大后需重评估 |
| 11 | 复盘格式 | Markdown 为唯一格式，渲染交给 Web | 通用、可 diff、可检索 | 复杂排版能力有限 |
| 12 | 三层结构 | 公司 → 岗位 → 轮次，不做无限树 | 查询与展示清晰 | 跨公司统计需额外设计 |
| 13 | 公司归一化 | 联想 + 用户确认，禁止自动合并 | 自动合并错误代价高 | 需要人工维护 |
| 14 | 前端风格 | 专业克制；五维用横向条形图，不用雷达图 | 可精确比较、中文标签排得下 | 视觉表现力有限 |
| 15 | 测试 | TDD；单元 ≥85%、关键类 ≥95%、契约 100% 端点、前端 Vitest + Playwright | 质量门禁可执行 | 初期搭建成本 |
| 16 | 跨设备 | 仓库唯一事实源；开工 pull + 读记忆，收工写记录 + push | 两台设备不共享本机记忆 | 依赖网络与提交纪律 |
| 17 | CI/CD | 先 CI（契约 / 后端 / 前端三 job），CD 延后 | M2 变更密度高，先防回归；CD 依赖主机环境 | CD 仍手工 |
| 18 | M2 契约分批 | 第一批场景/公司/岗位/对比，第二批面试/Offer | 单次评审 30+ 端点负担过大 | 第二批需保持风格一致 |
| 19 | 场景绑定 | 7 个 `LlmScene`；JD 解析与简历对比暂走全局默认 | 不擅自扩需求枚举；先保证确定性 | 后续可能需扩枚举 |
| 20 | 错误码 | 全局唯一，按 HTTP 状态分段 | 避免业务码语义冲突 | 新增码需同步契约与枚举 |

## 5. 实现地图（面试演示用）

### 5.1 后端关键类

| 位置 | 作用 | 面试可讲点 |
|---|---|---|
| `common/llm/OpenAiCompatibleClient` | 手写 `/chat/completions`、SSE、`/models`、JSON 模式 | 协议细节、错误脱敏、`max_tokens`、SSE 未收到 `[DONE]` 判失败 |
| `common/llm/StructuredOutputInvoker` | JSON 模式 + 本地修复 + 带错误反馈重试 ≤3 | 稳定性闭环，不是「祈祷模型输出 JSON」 |
| `common/llm/JsonOutputParser` | 去围栏、截取平衡 JSON、去尾逗号 | 字符级无副作用修复 |
| `infrastructure/llm/ProviderClientRegistry` | Provider 客户端缓存与精确失效 | 热更新、线程安全 |
| `infrastructure/security/AesGcmCipher` | API Key 加密 | 密钥管理、掩码、日志脱敏 |
| `modules/llm/*` | Provider / Model / 全局 / 场景 / 连通测试 | 双维度定位、上游模型列举 |
| `modules/chat/*` | 会话、切换守卫、SSE、消息追溯 | 409 状态机、取消与队列拒绝 |
| `modules/resume/*` | 上传、解析、异步分析、报告、删除 | SHA-256 去重、状态机、本地计分、级联清理 |
| `infrastructure/storage/LocalFileStorage` | 本地文件 + 路径穿越防护 | 存储抽象、后续 MinIO 演进 |
| `common/api/*` | 统一响应 / 错误码 / 异常 / traceId | 可观测性与错误契约 |

### 5.2 Prompt 与结构化输出

- 模板：`resources/prompts/resume-analysis-system.st` / `resume-analysis-user.st`。
- system 管角色、评分维度与权重、JSON 字段与约束；user 管数据注入，并用 `<<<RESUME ... RESUME>>>` 数据边界防注入。
- 请求：`response_format=json_object`、`temperature=0.2`、`max_tokens`（默认 4096）。
- 失败处理：本地修复 → 带错误原因重试 3 次 → 仍失败则任务 `FAILED`，不产出半份报告。
- 业务兜底：评分缺失直接失败、越界夹到 0~100、总分本地计算、列表长度兜底。
- 记录：每次调用写 `llm_call_logs`（scene/provider/model/token/耗时/成败）。

### 5.3 测试与质量门禁

| 层 | 内容 |
|---|---|
| 后端单元 | Service、网关、结构化输出、加密、文本清洗、状态机 |
| 后端契约 | `ContractSchemaTest` 字段一致；`ContractCoverageTest` 端点覆盖 + `x-implemented` 区分待实现 |
| 后端集成 | Testcontainers 起 PostgreSQL，验证 Flyway 与主链路 |
| 前端单测 | HTTP 解包、SSE 帧解析、主题等 |
| 前端 E2E | 接口全 mock；本机 Edge / CI Chromium |
| CI | 契约 lint / 后端测试 + JaCoCo / 前端构建 + 单测 + E2E；集成测试防跳过守卫 |

**M1 收口数据**：后端 88 tests、总行覆盖 91.49%；前端 9 Vitest + 6 E2E；契约 lint 0 error 0 warning。

**当前契约**：45 端点 / 80 schema；26 已实现、19 待实现（`x-implemented: false`）。

## 6. AI 协作实录

### 6.1 协作分工

| 角色 | 负责 |
|---|---|
| 项目作者 | 产品目标、范围取舍、验收标准、关键决策、最终代码审查 |
| AI | 代码检索、方案对比、契约与实现、测试与排障、文档记录、CI 配置 |

核心原则：**AI 可以提出方案，但不能替作者做产品决策；作者可以接受 AI 的实现，但必须能解释与验证。**

### 6.2 分阶段协作

**阶段 A：需求澄清**

- 作者先给目标与约束，AI 追问边界（单用户、是否 RAG、文件存储、模型来源、评分口径）。
- 有效模式：让 AI 先复述需求与缺口，再给 2~3 个方案与代价，作者拍板。
- 结果：需求从 v1.0 迭代到 v1.7，重要取舍全部有记录。

**阶段 B：契约先行**

- 作者要求「先改契约再实现，禁止实现完再补」。
- AI 完成 OpenAPI 3.1 契约后，作者要求核对端点、字段、错误码与旧契约兼容性。
- 有效模式：契约同时服务后端实现、前端类型生成、契约测试与 CI lint，形成四方一致。

**阶段 C：M1 实现**

- 按「骨架 → 模型网关 → 简历中心 → 前端收口」拆分，每阶段有可运行产物与测试。
- AI 在实现中主动补测试，但作者会在阶段末要求「再次确认真正收口」，独立复跑全量验证。

**阶段 D：M1 收口复审**

- 作者原话：「再次确认 M1 真正收口」。
- AI 不沿用上次结论，重新跑测试与覆盖率，发现并修复 SSE 取消、切换原子性、启动恢复、`max_tokens`、文件删除失败保留 DB 等问题。
- 结论：复审不是形式，独立复验能抓出「文档说完成、代码没闭环」的偏差。

**阶段 E：体验返工**

- 作者反馈：「新增服务商后连通测试提示没有模型；简历分析提示没有可用模型但不知道去哪设置。」
- AI 没有只改文案，而是补齐交互链路：创建后自动拉取上游模型、唯一模型自动设全局默认、多模型勾选、错误旁直达设置入口。
- 有效模式：把用户反馈转化为「流程缺口」，而不是「单点 bug」。

**阶段 F：CI 落地**

- 作者要求：「开工加 CI 时带上解释，说明每一步作用、CI 实际跑哪些测试、是契约决定还是 ci.yml 决定。」
- AI 在 workflow 每个 step 写明作用、失败含义、本地复现命令，并用首次 PR 真实暴露两个 Linux-only 问题。
- 有效模式：CI 不是「跑绿就完事」，而是教学与追溯材料。

**阶段 G：M2 契约与复验**

- 作者完成第一批契约后要求「验证是否有误和遗漏」。
- AI 独立比对旧契约、统计端点/schema、检查错误码与需求条款，发现版本号未升、错误码冲突、Prompt 版本缺失、`x-implemented` 说明缺失。
- 有效模式：让 AI 做「对抗性审查」，而不是「确认性审查」。

### 6.3 有效的协作指令模式

1. **目标 + 约束 + 验收标准**：例如「契约先行、单用户、错误码全局唯一、CI 0 warning」。
2. **先方案后实现**：「先同步方案，暂不实现」能在写代码前排除方向性错误。
3. **独立复验**：「不要沿用上次结论，重新验证」能发现文档与代码漂移。
4. **要求解释**：「每一步作用、失败含义、本地复现命令」迫使 AI 输出可验证知识。
5. **要求记录**：「把机制整理进需求文档 / 记录问题原因与修复」把对话变成资产。
6. **明确不做什么**：「这次只改文档」「不要动无关代码」控制范围。
7. **失败要根因**：不接受「重试成功」，要求现象、根因、修复、预防。

### 6.4 踩过的协作坑

| 坑 | 表现 | 应对 |
|---|---|---|
| 编辑工具「报告成功但未落盘」 | 12 处 `x-implemented` 首轮只写入 4 处 | 每处编辑后用 Grep/Read 复核；最终以构建/测试为准 |
| 并行编辑同一文件互相覆盖 | 多个 Edit 同时改契约，部分修改被后写覆盖 | 同一文件串行修改；复杂改动用脚本一次写入并断言 |
| 本地通过 ≠ CI 通过 | Windows 有 hoisted `yaml`、redocly 配置按 cwd 查找 | CI 用干净环境；命令与 cwd 保持一致 |
| 文档说完成 ≠ 代码闭环 | 契约版本写 1.6.0，文件仍是 1.5.0 | 用脚本/解析核对事实，不只看提交说明 |
| 后台任务拖慢构建 | Maven 从 1 分钟膨胀到 20+ 分钟 | 跑全量前先停无关 dev server / 旧构建 |
| 网络不稳导致 push 失败 | GitHub 直连/代理间歇失败 | 重试；失败写「待补推」标记，下次开工先补 |
| 过度相信 AI 的自我总结 | 总结说「已修复」，实际只改了局部 | 用测试、lint、grep、CI 运行结果做证据 |

## 7. 问题案例库（现象 → 根因 → 修复 → 预防）

### 案例 1：Testcontainers 与 Docker 29 不兼容

- **现象**：集成测试找不到 Docker 环境，报 client version 1.32 too old。
- **根因**：Testcontainers 1.21 内置 docker-java 默认 API 1.32，Docker 29 最低要求 1.44。
- **修复**：测试资源 `docker-java.properties` 固定 `api.version=1.44`。
- **预防**：要求 Docker Engine ≥25；升级 Testcontainers 后删除该配置。
- **证据**：`d5c802f`。

### 案例 2：本机 5432 被占用

- **现象**：后端连不上本地 PostgreSQL。
- **根因**：本机 PostgreSQL 与 Docker 同时占用 5432。
- **修复**：临时容器映射 5433，后端显式 `DB_URL` 指向 5433。
- **预防**：联调环境使用独立端口；Compose 默认端口在 README 说明。

### 案例 3：CI 契约 job 报 `Cannot find module 'yaml'`

- **现象**：CI 契约 job 失败，本机正常。
- **根因**：`redoc` 运行时需要 `yaml`，但锁文件没有；Windows 本机有历史残留被 hoisting 掩盖，CI `npm ci` 严格按锁文件安装。
- **修复**：显式添加 `yaml` devDependency。
- **预防**：CLI 依赖显式声明；新增工具后在干净环境跑 `npm ci`。
- **证据**：run `43830839548` 失败，`c0ce5f5` 修复，run `43831265961` 通过；详见 `docs/ci-cd-plan.md` §9。

### 案例 4：redocly 未加载根配置

- **现象**：在 `frontend/` 下执行 lint 出现 3 条本应关闭的警告。
- **根因**：redocly 从当前工作目录找配置，根 `redocly.yaml` 在上一级；本地之前在仓库根目录验证，掩盖了问题。
- **修复**：脚本显式 `--config ../redocly.yaml`。
- **预防**：共享配置显式传路径；本地复现与 CI 使用同一命令与 cwd。

### 案例 5：M2 错误码与后端冲突

- **现象**：契约复验时发现 `40903/40904/40905/40901` 被重复分配。
- **根因**：新增契约只看业务语义，没有核对后端 `ErrorCode` 既有占用。
- **修复**：改为 `40906` 公司存在、`40905` 公司被引用（复用通用码）、`40907` 分析未完成、`40908` 任务执行中，并同步枚举。
- **预防**：错误码全局唯一；新增码必须同时改契约与 `ErrorCode`；复验时做冲突扫描。
- **证据**：`803c15d`。

### 案例 6：契约版本号未真正升级

- **现象**：提交说明和 PROGRESS 都写 1.6.0，文件仍是 1.5.0。
- **根因**：只改文档描述，没有核对 YAML 实际字段。
- **修复**：`info.version` 改为 1.6.0。
- **预防**：版本、端点、schema 数量用脚本统计；提交前解析 YAML 复核。

### 案例 7：F7 缺少 Prompt 版本判定

- **现象**：需求要求「同一 Prompt 版本 + 同一模型」，契约只比较模型。
- **根因**：实现时未记录 Prompt 版本，契约按现状写。
- **修复**：契约新增 `promptVersion` / `promptVersionMismatch`；V3 需给 `resume_analyses` 加列。
- **预防**：需求条款逐条对照契约；实现与需求有偏差时显式记录，不静默降级。

### 案例 8：Playwright strict mode 冲突

- **现象**：E2E 断言 `公司内网网关` 匹配到两个元素。
- **根因**：全局默认栏和 Provider 卡片都包含该文本。
- **修复**：限定 `page.locator('.provider').filter(...)`。
- **预防**：E2E 选择器优先限定容器，不依赖全局唯一文本。

### 案例 9：M1 复审发现的状态机问题

- **现象**：SSE 取消后会话可能停在 `PROCESSING`；切换模型存在竞态；重启后遗留任务不回收。
- **根因**：只覆盖正常路径，没有处理取消、异常结束、重启恢复。
- **修复**：原子条件切换、取消释放、启动恢复、坏 SSE 帧显式失败、`max_tokens` 上限。
- **预防**：状态机必须有「异常路径测试」；收口复审独立复跑。
- **证据**：`98ef7a4` `db1f615`。

### 案例 10：模型配置引导缺失

- **现象**：新增服务商后测试提示「没有模型」；简历分析提示「没有可用模型」但用户不知道去哪设置。
- **根因**：后端只认已登记模型，前端没有创建后拉取与设置入口。
- **修复**：自动拉取上游模型、唯一模型自动全局默认、多模型勾选、错误旁「打开模型设置」。
- **预防**：功能验收要按「新用户第一次使用」走一遍，而不是只测已有配置。

### 案例 11：编辑工具假成功与并行覆盖

- **现象**：工具返回成功，但文件未落盘；多个编辑同时改同一文件，后写覆盖前写。
- **根因**：本机编辑链路不稳定 + 并行修改同一文件。
- **修复**：每步 Grep/Read 复核；同一文件串行编辑；批量修改用脚本并断言替换次数。
- **预防**：以构建/测试/解析结果为准，不以「编辑成功」提示为准。

### 案例 12：Maven 构建异常变慢

- **现象**：`mvn testCompile` 从约 1 分钟膨胀到 20 多分钟。
- **根因**：多个后台任务（vite dev、旧 Spring Boot、旧 Maven）并行占用资源。
- **修复**：跑全量前停无关后台任务。
- **预防**：构建前检查后台进程；CI 与本地分开跑。

## 8. AI 编程方法论（可复用）

### 8.1 十条原则

1. **事实源分层**：代码 > 契约 > 需求文档 > 进度文档 > AI 记忆；冲突时以代码为准并修正上层文档。
2. **契约先行**：接口先写契约，再实现、生成类型、加契约测试。
3. **测试先行**：先写失败测试，再实现；关键模块覆盖门禁。
4. **证据优先**：任何「已完成」都要有命令输出、CI 运行或可复现步骤支撑。
5. **小步提交**：一个可验证的闭环一次提交，提交信息写「为什么」。
6. **独立复验**：阶段末不复用上次结论，重新跑全量验证。
7. **文档即记忆**：决策、问题、验证写入仓库，不依赖对话上下文。
8. **明确边界**：一次只改请求范围内；不确定的产品取舍先问。
9. **异常路径优先**：取消、超时、重启、重复请求、并发冲突都要有测试。
10. **人类做决策**：AI 给选项与代价，产品范围与优先级由人拍板。

### 8.2 一个可复用的工作流

```text
开工
  → git pull；读进度与会话；核对代码现状
  → 复述目标、约束、验收标准；列出不确定项

设计
  → 2~3 个方案 + 代价；先写方案/契约，不急着写代码
  → 明确不做什么（范围控制）

实现
  → 先测试后实现；小步提交
  → 关键路径加日志/追踪；异常路径同样覆盖

验证
  → 本地命令 → 全量测试 → CI
  → 阶段末独立复验；用脚本核对事实（版本、数量、错误码）

收工
  → 更新进度与会话记录；记录问题根因与预防
  → commit + push；失败留待补推标记
```

### 8.3 常见反模式

- 只给一句「帮我实现」，没有验收标准。
- 让 AI 一次改很多文件，无法审查。
- 只看 AI 总结，不看测试与运行结果。
- 本地通过就认为 CI 通过（环境差异）。
- 需求文档只改正文，不写迭代记录。
- 为了让测试变绿而改测试，而不是改实现。
- 把「能跑」当「可维护」：没有错误处理、日志、边界测试。
- 过度依赖框架/Agent 编排，核心协议与失败路径不透明。

### 8.4 可以量化的指标

| 指标 | 本项目现状 | 用途 |
|---|---|---|
| 后端测试数 / 覆盖率 | 88 / 91.49%（M1 收口） | 防止回归 |
| 前端单测 / E2E | 9 / 6 | 交互回归 |
| 契约端点 / 待实现 | 45 / 19 | 进度与范围 |
| CI 三 job | 每次 push/PR | 强制验证 |
| 复验发现问题数 | M2 第一批复验 4 个 | 衡量「完成」质量 |

## 9. 面试项目包装（Agent / LLM 应用开发岗）

### 9.1 30 秒介绍

> 我做了一个个人自用的 AI 求职平台「职点」，覆盖简历分析、岗位匹配、模拟面试和面试复盘。后端是 Java 21 + Spring Boot + PostgreSQL，前端 Vue3。模型层是数据库驱动的多 Provider / 多模型网关，支持热切换、SSE 流式、结构化 JSON 输出与失败重试。项目全程用 AI 结对开发，我用契约先行、测试门禁、CI 和独立复验来控制质量。

### 9.2 5 分钟演示脚本

1. **简历中心**：上传简历 → 自动分析 → 五维报告、优势短板、岗位方向。
2. **设置抽屉**：新增 Provider → 自动拉取上游模型 → 设全局默认 → 连通测试。
3. **模型对话**：新建会话 → 发送 → SSE 流式 → 切换模型 → 执行中切换返回 409。
4. **工程质量**：打开 GitHub Actions，展示契约 lint、后端测试 + 覆盖率、前端构建 + E2E 三个 job。
5. **契约**：展示 `openapi.yaml` 与前端生成类型、后端契约测试的对应关系。

### 9.3 与 Agent 岗位的能力映射

| Agent 岗位关注点 | 本项目对应能力 |
|---|---|
| LLM 协议与流式 | 手写 OpenAI 兼容客户端、SSE、`/models`、JSON 模式、`usage` |
| 上下文与 Prompt | system/user 分工、数据边界防注入、固定维度与权重、低温度 |
| 结构化输出 | JSON 修复、带错误反馈重试、AI DTO 与业务实体分离、本地校验 |
| 模型路由 | 多 Provider / 多 Model、热更新、场景级绑定、全局回落 |
| 可靠性 | 状态机、重试上限、取消/超时/重启恢复、失败降级 |
| 可观测性 | traceId、`llm_call_logs`、token/耗时/成败 |
| 评测与质量 | 契约测试、单元/集成/E2E、覆盖率门禁、CI |
| 工程化 | 契约先行、迁移管理、AES-GCM 密钥、路径穿越防护 |

**诚实边界**：这不是多智能体系统，没有 Planner / Tool Calling / 长期记忆。原因是当前业务是确定性流程，用状态机比 Agent 编排更可控、更便宜。若要做 Agent 化，下一步是工具调用、任务规划、记忆与评测集，而不是为了「像 Agent」而加编排。

### 9.4 可讲的 STAR 故事

1. **契约先行防漂移**：M1 契约 26 端点 → 前端类型生成 + 后端契约测试 + CI lint；M2 第一批扩到 45 端点，用 `x-implemented` 区分待实现。
2. **结构化输出稳定性**：JSON 模式 + 本地修复 + 错误反馈重试 + 本地计分；模型不能改维度与权重。
3. **模型热切换**：数据库驱动 Provider/Model，缓存精确失效，无需重启；执行中禁止切换。
4. **CI 首次运行抓出环境差异**：Linux 干净环境缺 `yaml`、redocly 配置按 cwd 丢失；修复后写进追溯文档。
5. **对抗性复验**：M2 契约复验发现版本号、错误码冲突、Prompt 版本缺失，而不是「确认完成」。

### 9.5 高频追问与回答要点

**Q：为什么不用 Spring AI / LangChain4j？**
A：核心复杂度是热更新、结构化加固、分层降级，这些框架不直接提供，且会遮蔽协议细节；手写客户端只依赖标准协议，便于排障与替换。LangChain4j 保留为备选。

**Q：怎么保证模型稳定输出 JSON？**
A：四层：JSON 模式 + 低温度；本地修复；带错误原因重试；业务侧 DTO 校验与本地计分。最终失败则任务 `FAILED`，不产出半成品。

**Q：怎么防 Prompt 注入？**
A：用户资料放数据边界，system 明确「只作为数据、不执行指令」；输出再经结构化校验；关键业务字段不接受模型自由发挥。

**Q：为什么不做 RAG / 多智能体？**
A：当前数据量远小于上下文窗口，RAG 收益低；业务流程确定，状态机比 Agent 编排更可控。等数据量与任务开放性上来再评估。

**Q：你怎么评估 AI 输出质量？**
A：目前靠固定维度、权重、结构化校验和人工真实模型评估；没有自动 LLM-as-judge 评测集，这是后续要补的。

**Q：AI 写了多少代码？你怎么保证自己理解？**
A：AI 深度参与实现，但我负责目标、契约、验收与复验；每阶段要求 AI 解释步骤与失败含义，关键路径用测试、CI、手工复现验证。面试中能讲清每个设计取舍与失败案例。

**Q：最大的不足？**
A：单用户无鉴权、M2 尚未实现、缺少自动评测集与 CD；AI 协作下需要更强的验证纪律，这些都在文档里如实记录。

## 10. 维护约定

1. **何时更新**：里程碑完成、重大设计变更、重要 bug 修复、面试准备、方法论有新结论时。
2. **怎么写**：追加新章节或案例，不改旧结论；带日期、提交/运行 ID、文件链接。
3. **与其它文档**：
   - 需求变化 → 需求文档「迭代历程」；
   - 接口变化 → `contracts/openapi.yaml`；
   - 进度/阻塞 → `PROGRESS.md`；
   - 当日过程 → `sessions/YYYY-MM-DD-<主机名>.md`；
   - 本文件 → 跨阶段的叙事、案例与方法论。
4. **不写**：密钥、token、个人隐私、未经证实的结论。
5. **证据优先**：凡是「已修复/已通过」，必须能指向测试、CI 或代码。
